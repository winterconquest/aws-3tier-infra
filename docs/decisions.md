## 네트워크

### AZ별 독립 NAT Gateway

**배경**

프라이빗 서브넷의 App 인스턴스가 외부로 나가려면 NAT Gateway가 필요하다.
NAT는 AZ 단위 리소스이므로 몇 개를 어디에 둘지 정해야 했다.

**검토한 선택지**

| 방식 | 장점 | 단점 |
|---|---|---|
| 단일 NAT | 비용 절반 | 해당 AZ 장애 시 전체 App 계층 아웃바운드 중단 |
| AZ별 NAT | AZ 장애 격리 | 비용 2배, AZ 수만큼 증가 |

**결정**

AZ별로 NAT Gateway를 배치하고, 각 AZ의 프라이빗 라우팅 테이블이 같은 AZ의 NAT를 향하도록 했다.

**트레이드오프**

NAT Gateway 시간 요금이 이 프로젝트 비용의 23%를 차지한다(측정치는 [README 비용](../README.md#비용) 참고).
단일 NAT로 줄이면 절반을 절감할 수 있다. Multi-AZ 구성의 목적이 AZ 장애 격리인데
NAT를 단일화하면 그 목적이 훼손되므로, 가용성을 우선했다.

**검증**

각 AZ의 인스턴스에서 아웃바운드 공인 IP가 서로 다름을 확인했다.

**재검토 조건**

- 개발/검증 환경처럼 AZ 장애 허용이 가능한 경우 → 단일 NAT
- S3/DynamoDB 트래픽이 대부분인 경우 → VPC Endpoint로 NAT 경유 자체를 줄임
- 아웃바운드가 거의 없는 워크로드 → NAT 제거 검토

### 보안 그룹 source를 SG 참조로 지정

App 계층 EC2의 ingress를 CIDR이 아니라 ALB 보안 그룹 참조로 지정했다. CIDR 방식은
같은 서브넷의 다른 인스턴스까지 허용 범위에 들어가지만, SG 참조는 ALB를 경유한
트래픽만 통과시킨다. 실제로 같은 VPC·같은 SG에 속한 인스턴스 간 직접 접근이
차단되는 것을 확인했다.

서브넷 CIDR이 바뀌어도 규칙을 수정할 필요가 없다는 부수 효과도 있다.

## 접근 제어

### Bastion 대신 SSM Session Manager

프라이빗 서브넷 인스턴스에 접근하는 방법으로 Bastion 호스트와 SSM Session Manager를
검토했다. SSM을 택한 이유는 **인바운드 포트를 하나도 열지 않아도 된다**는 점이다.
에이전트가 아웃바운드로 SSM 엔드포인트에 연결을 유지하는 구조이므로 NAT만 있으면
동작한다. SSH 키 관리가 없고 접속 이력이 CloudTrail에 남는다는 점도 이유가 됐다.

대신 SSM 엔드포인트에 대한 아웃바운드 경로가 필수이고, 세션 시작에 IAM 권한이
필요하다. 폐쇄망이라면 VPC Endpoint(Interface형)를 추가해야 한다.

### 계정 설정 의존을 코드로 이관

**발견**

프라이빗 서브넷의 App 인스턴스에 SSM Session Manager로 접속이 되는 것을 확인한 뒤,
Launch Template에 인스턴스 프로파일이 붙어 있지 않다는 점이 눈에 띄었다. 정상이라면
연결될 수 없는 조합이다.

```bash
aws ec2 describe-launch-template-versions --versions 2 \
  --query "LaunchTemplateVersions[].LaunchTemplateData.IamInstanceProfile"
# []
```

에이전트가 사용 중인 역할을 확인하니 계정 수준의 서비스 역할이었다.

```bash
aws ssm describe-instance-information --query "InstanceInformationList[].IamRole"
# service-role/AWSSystemsManagerDefaultEC2InstanceManagementRole
```

Default Host Management Configuration(DHMC)이 활성화되어 있었다. 인스턴스 프로파일이
없는 EC2에 계정 단위 역할을 적용해 SSM 관리 대상으로 만드는 기능이다. SSM 연결 문제를
디버깅하는 과정에서 콘솔로 켰던 것이 원인이었고, 그 시점에는 AMI 문제로 에이전트 자체가
없어 효과가 없었다. AMI를 수정하자 그제서야 이 경로로 연결이 성립했다.

**문제 인식**

동작 자체는 정상이었다. 문제는 **그 동작이 Terraform 코드가 아니라 계정 설정에
의존하고 있었다는 점**이다.

이 상태에서 다른 사람이 리포지토리를 clone해 `apply`하면, DHMC가 꺼진 계정에서는
SSM 접근이 성립하지 않는다. 코드에 드러나지 않는 전제 조건이 숨어 있는 셈이고,
이는 이 프로젝트의 첫 번째 목표인 재현 가능성에 정면으로 어긋난다.

문서에도 영향이 있다. "Bastion 없이 SSM으로 접근하며 필요한 IAM 역할을 Terraform으로
관리한다"고 기술할 계획이었는데, 코드에 역할이 없는 상태에서는 사실과 다른 진술이 된다.

**결정**

필요한 IAM 리소스를 `iam.tf`로 정의하고 Launch Template에 연결했다.

| 리소스 | 역할 |
|---|---|
| `aws_iam_role` | trust policy로 EC2 서비스의 AssumeRole 허용 |
| `aws_iam_role_policy_attachment` | `AmazonSSMManagedInstanceCore` 연결 |
| `aws_iam_instance_profile` | EC2에 역할을 전달하는 컨테이너 |

동시에 계정의 DHMC 설정을 기본값으로 되돌렸다.

```bash
aws ssm reset-service-setting \
  --setting-id arn:aws:ssm:<region>:<account>:servicesetting/ssm/managed-instance/default-ec2-instance-management-role
```

**검증**

DHMC를 끄지 않은 채로 프로파일만 추가하면 어느 쪽 덕분에 동작하는지 구분할 수 없다.
인스턴스 프로파일은 DHMC보다 우선 적용되므로, 두 설정이 공존해도 겉으로는 같은 결과가
나오기 때문이다. 따라서 **DHMC를 먼저 해제한 뒤 인스턴스를 교체해 재검증했다.**

교체된 인스턴스에 프로파일이 정상 연결되고 SSM 접속이 유지되는 것을 확인했다.

**트레이드오프**

DHMC는 계정 내 모든 EC2를 한 번에 SSM 관리 대상으로 만들 수 있어 운영 편의성이 높다.
인스턴스마다 프로파일을 붙이는 것보다 관리 지점이 적고, 프로파일 누락으로 인한
접근 불가 상황도 방지된다.

그럼에도 프로파일 방식을 택한 이유는, **이 프로젝트가 인프라 전체를 코드로 표현하는
것을 목표로 하기 때문**이다. 계정 설정은 Terraform state 밖에 있어 변경 이력이 남지
않고, 다른 계정이나 리전에 그대로 이식되지도 않는다.

**남은 원칙**

- **동작한다는 사실만으로 구성이 올바르다고 볼 수 없다.** 무엇 때문에 동작하는지
  설명할 수 없으면, 무엇 때문에 깨질지도 알 수 없다.
- 디버깅 과정에서 콘솔로 변경한 설정은 원인이 해소된 뒤 되돌려야 한다. 되돌리지
  않으면 그 설정이 구성의 일부가 되어버리고, 코드와 실제 상태가 어긋난다.
- 검증할 때는 **검증하려는 요소만 남기고 대체 경로를 차단한다.** 그렇지 않으면
  무엇이 동작을 성립시켰는지 확정할 수 없다.

**재검토 조건**

- 계정 내 EC2가 많고 프로파일 누락으로 인한 관리 사각지대가 실질적 위험이 되는
  환경이라면, DHMC를 기본 안전망으로 두고 프로파일을 개별 적용하는 조합이 합리적이다.
  이 경우 DHMC 활성화 자체를 코드나 계정 부트스트랩 절차로 관리해야 한다.
- 여러 계정을 운영한다면 Organizations 수준에서 일괄 설정하는 방식도 검토 대상이다.

## Terraform

### AMI를 SSM public parameter로 조회

초기에는 `aws_ami` 데이터 소스에 이름 패턴 필터를 사용했으나, 패턴이
`al2023-ami-minimal-*`까지 매칭되어 SSM 에이전트가 없는 minimal 이미지가 선택되는
문제가 발생했다. SSM public parameter는 AWS가 이미지 종류별로 별도 경로를 제공하므로
이런 혼입이 구조적으로 발생하지 않는다.

파라미터 경로가 모든 리전에서 동일해 리전 이식성이 확보된다는 것이 더 큰 이점이다.

다만 "최신 이미지"를 조회하는 방식이므로 apply 시점에 따라 결과가 달라지는 비결정성은
남는다. 운영 환경이라면 AMI ID를 고정하고 계획적으로 갱신하는 편이 안전하다.

### Launch Template 버전 관리 방식

Terraform이 `aws_launch_template`을 수정하면 새 버전을 생성하지만 기본 버전을
자동으로 올리지는 않는다. ASG가 `$Default`를 참조하는 상태에서는 인스턴스를 교체해도
계속 이전 버전으로 기동된다.

`update_default_version = true`를 지정해 새 버전이 기본 버전이 되도록 했다.
ASG에서 `latest_version` 속성을 직접 참조하는 방식도 가능하며, 이 경우 롤백 시
기본 버전을 콘솔에서 되돌리지 않고 코드 수정으로 처리할 수 있다는 장점이 있다.

## 모니터링

### 알람의 역할 분리

**배경**

ALB 타겟 상태를 감시하는 알람을 구성하면서, 임계값과 지속 시간을 얼마로 잡을지
정해야 했다. ASG 자가치유가 활성화되어 있으므로 인스턴스 하나가 죽어도 3~5분 내에
자동 복구된다. 이 상황에 알람을 울릴 것인가가 핵심 질문이었다.

**판단 기준**

알람의 목적을 **"지표가 임계값을 넘었음을 알리는 것"이 아니라 "사람이 개입해야 하는
시점을 알리는 것"** 으로 정의했다.

자동으로 복구되는 상황에 알람이 울리면 수신자는 할 일이 없다. 이런 알람이 반복되면
알람 자체를 무시하게 되고, 실제 대응이 필요한 시점에도 반응하지 않게 된다. 알람의
가치는 개수가 아니라 **신뢰도**에서 나온다.

동시에 아무것도 알리지 않으면 자가치유가 실패하는 경우를 놓친다. 두 요구가 충돌한다.

**검토한 선택지**

| 방식 | 장점 | 단점 |
|---|---|---|
| 단일 알람, 짧은 임계 | 빠른 인지 | 자가치유 성공 시에도 발화 → 노이즈 |
| 단일 알람, 긴 임계 | 노이즈 없음 | 이상 징후를 늦게 인지, 상황 파악 지연 |
| 알람 2개로 분리 | 인지와 대응 판단을 구분 | 알람 개수 증가, 설계 복잡도 상승 |

**결정**

성격이 다른 두 알람으로 분리했다.

| 알람 | 지표 | 조건 | 역할 |
|---|---|---|---|
| `alb-unhealthy` | `UnHealthyHostCount ≥ 1` | 3분 중 1회 | **조기 경보** — 이상이 발생했음을 알림 |
| `alb-healthy` | `HealthyHostCount < 2` | 6분 연속 | **SLO 위반** — 자동 복구가 실패했음을 알림 |

`alb-healthy`의 6분은 자가치유 소요 시간(3~5분)에 여유를 더한 값이다. 이 시간 안에
복구되면 발화하지 않는다.

두 알람은 수신자에게 다른 의미를 전달한다. 조기 경보는 "지켜볼 것", SLO 위반은
"조치할 것"이다. `alarm_description`에도 각각 다른 확인 절차를 기술했다.

**검증**

웹서버 프로세스를 중지해 장애를 발생시킨 결과, 설계 의도대로 동작했다.

| 시각 | 사건 |
|---|---|
| 21:41:46 | 웹서버 중지 |
| 21:44:01 | 신규 인스턴스 healthy (자가치유 완료) |
| 21:44:34 | `alb-unhealthy` → ALARM |
| 21:47:34 | `alb-unhealthy` → OK |

**`alb-healthy`는 발화하지 않았다.** 자가치유가 6분 안에 완료됐기 때문이며,
불필요한 알람을 억제하는 설계가 실제로 작동함을 확인한 결과다.

자가치유 완료(21:44:01)보다 알람 발화(21:44:34)가 늦다. CloudWatch 지표 발행과
알람 평가에 지연이 있어, 알람은 본질적으로 사후 통보다. 즉시 대응이 필요한
시스템이라면 알람이 아니라 자동화된 복구 장치가 우선이다.

발화하지 않은 알람도 검증 대상이라는 점이 중요하다. 울리지 않은 이유가 "설계대로"인지
"고장나서"인지는 구분되어야 한다. 이 경우 `alb-unhealthy`가 같은 사건에 정상 발화했으므로
지표 수집과 알람 평가 자체는 동작하고 있었음이 함께 확인된다.

**트레이드오프**

알람이 2개가 되면서 관리 대상이 늘었고, 두 알람의 임계값이 서로 정합성을 유지해야 한다.
`alb-healthy`의 임계값 2는 ASG desired capacity와 연동되므로, 용량을 3으로 늘리면
알람도 함께 수정해야 한다. 현재는 코드에 상수로 들어가 있어 자동으로 따라가지 않는다.

또한 조기 경보는 자가치유가 정상 동작하는 상황에서도 매번 발화한다. 인스턴스 교체가
빈번한 환경에서는 이 알람이 다시 노이즈가 될 수 있다.

**재검토 조건**

- ASG desired capacity를 변경하는 경우 `alb-healthy` 임계값을 함께 조정한다.
  변수로 참조하도록 개선하면 이 연동이 자동화된다.
- 배포나 스케일링으로 인스턴스 교체가 잦아지면 조기 경보를 알림 대상에서 제외하고
  대시보드 관측용으로만 사용하는 것을 검토한다.
- 알림 채널을 분리할 수 있다면 조기 경보는 채팅 채널로, SLO 위반은 호출 가능한
  경로로 보내는 구성이 목적에 더 부합한다.

### treat_missing_data를 지표별로 다르게 설정

지표가 도착하지 않을 때 정상으로 볼지 위반으로 볼지는 **그 지표가 무엇을 세는지**에
따라 달라진다.

| 알람 | 설정 | 근거 |
|---|---|---|
| `alb-unhealthy` | `notBreaching` | 이상 징후를 세는 지표. 데이터가 없으면 이상도 없다 |
| `alb-healthy` | `breaching` | 정상 용량을 세는 지표. 데이터가 없으면 정상임을 확인할 수 없다 |
| `rds-freestorage` | `breaching` | 지표 중단은 인스턴스 자체의 문제를 시사한다 |

기본값 `missing`은 판단을 보류하므로, 결측이 장애를 의미하는 지표에는 부적합하다.

다만 `notBreaching`이 실제 장애를 침묵시킨 사례가 있었다.
[지표 선택 오류와 재설계](#지표-선택-오류와-재설계) 참고.

### 지표 선택 오류와 재설계

**문제**

`alb-unhealthy` 알람을 구성한 뒤 인스턴스를 강제 종료해 검증했으나, 알람이 ALARM으로
전환되지 않았다. 알람 이력에는 apply 직후의 `INSUFFICIENT_DATA → OK` 기록만 있었다.

**진단 과정**

원인이 될 수 있는 구간을 하나씩 배제했다.
처음 인지한 증상은 "알람 메일이 오지 않는다"였다. 전달 경로부터 배제해 나갔다.

| 단계 | 확인 방법 | 결과 |
|---|---|---|
| 알림 전달 경로 | `sns publish`로 테스트 발송 | 정상 수신 → SNS·구독 문제 아님 |
| 알람 발화 여부 | `describe-alarm-history` | 상태 전환 기록 없음 → 알람이 울리지 않았음 |
| 지표 원본 | `get-metric-statistics` 90분 조회 | 장애 시각 전후 2분간 **데이터 미발행** |

세 번째 단계가 결정적이었다. 지표 값이 0으로 유지된 것이 아니라 발행 자체가 끊겨 있었다.

**원인**

세 가지가 겹쳤다.

1. **지표가 세는 대상을 잘못 이해했다.** `UnHealthyHostCount`는 *등록된 타겟 중
   health check에 실패한 것*의 개수다. 인스턴스를 종료하면 타겟이 등록 해제되므로
   셀 대상 자체가 사라진다. 지표가 오르지 않고 없어진다.
2. **장애 순간에 지표가 결측된다.** 타겟 등록 해제 과정에서 ALB가 해당 지표를
   발행하지 않는 구간이 생긴다.
3. **`treat_missing_data = notBreaching`이 그 구간을 정상으로 처리했다.**
   트래픽이 없을 때의 노이즈를 막으려고 선택한 값이, 실제 장애 시점을 침묵시켰다.

**수정**

지표를 바꾸지 않고 **검증 방법을 바꿨다.** 인스턴스 종료 대신 웹서버 프로세스만 중지한다.

```bash
sudo systemctl stop httpd
```

인스턴스가 살아 있어 타겟 등록이 유지되므로 `UnHealthyHostCount = 1`이 지속 발행되고,
복구 시점도 제어할 수 있다. 이 방식으로 재검증한 결과 알람이 정상 발화했다.

추가로 `datapoints_to_alarm = 1`을 적용했다. 짧게 지나가는 이벤트를 3분 창 안에서
한 번만 관측해도 발화하도록 하기 위해서다.

**지표 선택 기준**

두 지표는 같은 것을 다른 각도에서 본다.

| 지표 | 세는 대상 | 감지에 적합한 상황 |
|---|---|---|
| `UnHealthyHostCount` | 등록된 타겟 중 실패한 것 | 앱이 응답하지 않음 (프로세스 다운, 응답 지연) |
| `HealthyHostCount` | 정상 응답하는 타겟 | 타겟이 사라짐 (인스턴스 소실, 용량 미달) |

**사라진 것을 세는 지표와 실패한 것을 세는 지표는 다르다.** 인스턴스 소실은
`HealthyHostCount`가 줄어드는 것으로 관측해야 한다. 이 프로젝트는 두 알람을 모두
구성했으므로 양쪽 상황이 각각 다른 알람으로 커버된다.

**남은 원칙**

- 알람을 만든 뒤 **의도한 장애를 일으켜 발화를 확인하기 전까지는 동작한다고 볼 수 없다.**
  "알람이 있다"와 "알람이 동작한다"는 다르다.
- 지표를 고를 때 이름이 아니라 **무엇을 세는지**를 확인한다. 특히 개수 지표는
  대상이 사라졌을 때 0이 되는지, 발행이 끊기는지가 다르다.
- `treat_missing_data`는 노이즈 방지 관점만으로 정하면 안 된다. 결측이 발생하는
  상황이 정상인지 장애인지 먼저 판단해야 한다.

**재검토 조건**

- 현재 health check는 `interval 30초 × unhealthy_threshold 3`이므로 타겟이 unhealthy로
  판정되기까지 최대 90초가 걸린다. 알람의 감지 지연(약 2분)에 이 시간이 더해지므로,
  실제 인지까지는 3분 이상 소요된다. 더 빠른 감지가 필요하면 interval을 줄여야 하지만
  타겟 부하와 일시적 지연에 대한 민감도가 함께 올라간다.
- 타겟이 자주 교체되는 환경(스팟 인스턴스, 빈번한 배포)에서는 `UnHealthyHostCount`
  기반 알람의 감지 창이 더 짧아질 수 있다. 이 경우 `HealthyHostCount` 쪽에 무게를 둔다.
- health check path가 `/`의 정적 응답이므로 **웹서버 프로세스 생존만 확인한다.**
  DB 연결 실패처럼 앱은 떠 있으나 기능하지 못하는 상태는 감지되지 않는다.
  실제 의존성을 점검하는 health check 엔드포인트를 두면 이 범위가 넓어진다.

| 항목 | 결정 | 근거 |
|---|---|---|
| 서브넷 3계층 분리 | Public/App/DB를 별도 서브넷으로 | 계층별 라우팅과 접근 제어를 독립적으로 관리 |
| TLS 종단 위치 | CloudFront에서 종단, ALB는 HTTP 수신 | 엣지에서 TLS 처리, 인증서 관리 지점 단일화 |
| IAM 정책 | AWS 관리형 `AmazonSSMManagedInstanceCore` 사용 | 초기 구성 속도 우선. 운영 시 고객 관리형으로 축소 필요 |
| trust policy 작성 | `jsonencode()` 인라인 | 정책 JSON 구조를 코드에 직접 노출. 정책이 늘면 `aws_iam_policy_document`로 전환 |
| 코드 구조 | 리소스 타입별 플랫 파일, 모듈 미사용 | 단일 환경에서는 모듈화 이득이 작음. 환경 분리 시 재검토 |
| lock 파일 | `.terraform.lock.hcl` 커밋, state·tfvars 제외 | provider 버전 고정은 재현성 요건, 나머지는 민감 정보 포함 |
| state 관리 | 로컬 파일 | 단독 작업 기준. CI/CD 도입과 함께 S3 backend + DynamoDB lock으로 전환 |
| 알람 임계값 | 하드코딩 대신 변수 기반 계산식 | 스토리지 크기 변경 시 비율이 자동 유지 |
| ASG health check | `health_check_type = ELB` | 인스턴스는 살아있고 앱만 죽은 상황도 교체 대상에 포함 |
| ASG 그룹 지표 | `enabled_metrics` 명시 | 기본 비활성이라 자가치유 관측이 불가능 |
| 대시보드 정의 | heredoc + 리소스 참조 | 콘솔에서 생성한 JSON을 그대로 이관. 동적 조립이 필요하면 `jsonencode` |
| 대시보드 EC2 위젯 | SEARCH 표현식 | 인스턴스 교체 시 ID 하드코딩은 유지 불가. 종료 인스턴스 잔존은 한계 |
| RDS Multi-AZ | 유지 | 페일오버 동작 검증이 목적. 개발 환경이라면 Single-AZ |
| 리포팅 | CloudWatch 대시보드 + `describe-alarm-history` | 대시보드는 알람 이력 집계 불가. 정기 리포팅에는 Grafana 등 별도 도구 필요 |
